@ABSTRACT 隨著全球資安威脅遽增，資安長（CISO）常面臨情資聲量浩大、卻缺乏在地化脈絡與處置指南的困境。本研究針對此痛點開發「CTI 資安風險決策支援平台 · CISO Dashboard」，收錄 TWCERT、iThome 與 The Hacker News 共 788 篇情資語料，以 TF-IDF 特徵向量化與 K-Means 演算法梳理威脅主題叢集，並抽取 288 個 CVE 對照 CISA KEV、FIRST EPSS、CVSS 與 MITRE CWE 四項官方資料。系統以可解釋加權模型評分——文章採四因子（50／30／12／8）、即時評估採五因子——自動派發 P1–P3 處置優先級與回應 SLA（24 小時／7 天／30 天），並附處置劇本（Playbook）。回測顯示，系統排序已遭利用漏洞之能力（交叉驗證 AUC 0.853）優於單用 CVSS（0.561）；規則式分類 held-out 準確率 73%（Cohen's κ=0.818）。平台另提供全球盲點補強，量化語料對時間窗內 KEV 之覆蓋僅 11%。後端以 FastAPI 與 SQLite 實作並部署於 Render 雲端。

#1 1. 研究動機與背景（權重 15%）
當前企業資安的核心困境，是「情資海量卻無法落地」。全球威脅情資源源不絕——The Hacker News 每月發布約 250 篇安全新聞，TWCERT/CC 與 iThome 持續產出在地公告——但資安長（CISO）與部署團隊缺乏時間逐一梳理，且國際平台普遍缺乏在地化企業環境脈絡。本專題語料橫跨 2024 年 1 月至 2026 年 11 月共 788 篇情資，涵蓋 783 件去重事件；其中標題含 CVE 者僅約一成，絕大多數新聞並不直接告訴工程師「要修什麼」。
更根本的問題在於「嚴重度與利用風險不對等」：企業慣以 CVSS 排序修補，但 CVSS 衡量漏洞本身嚴重度，與「是否真的被攻擊」無關。本專題以 CISA KEV 為「已遭實際利用」的事實依據回測：僅用 CVSS 排序的交叉驗證 AUC 只有 0.561，幾乎等於隨機；僅用 EPSS 為 0.827；本系統加權模型達 0.853。換言之，只看 CVSS，有一半的修補順序是錯的。
綜整實務訪查與資料觀察，本專題將痛點歸納為五項：情資量遠大於處理量、不知道哪個先修、修補期限沒有依據、在地情資被忽略（台灣來源僅占 21%）、決策無法稽核。本章後續各章即依序回應這五個痛點。

#1 2. 系統方法與實作過程（權重 30%）
#2 2.1 系統架構與技術棧
系統採五層架構：資料來源層、語料層、情資對照層、決策層與介面層，如圖 1 所示。資料來源層整合 The Hacker News、TWCERT/CC 與 iThome；語料層以 SQLite 儲存並去重；情資對照層將 CVE 與 EPSS、KEV、CVSS、CWE 快照及企業資產清單比對；決策層執行主題分群、規則分類、可解釋評分與修補優先級推算；介面層以 FastAPI 提供八個 REST 端點，前端採原生 JavaScript 與 Chart.js。分層的理由是「每層可獨立驗證」：錯誤可被定位到層級而非整座系統。後端部署於 Render 雲端平台，示範站隨原始碼推送自動更新。

#2 2.2 情資採集與語料建置
語料建置面對兩個實務限制：若依抓取順序取樣，語料會被最近兩個月塞滿（原始版本 77% 集中於近二月）；iThome 深層頁面有 403 限制且 robots 規範禁止系統性抓取，故僅保留近期 50 篇。本專題採分層取樣：每月固定抽取 15 篇國際與 5 篇台灣情資，將 35 個月鋪平。語料分兩層：平衡對照樣本 200 篇（台灣 100：國際 100）供台／國結構比較；自然語料 588 篇依真實發布比例收錄。兩層並存的原因有二：只用自然語料，台灣僅占 21%，跨區比較會被國際量體淹沒；只用平衡樣本則放大急迫性——P1 占比 20% 對自然語料的 3%，相差約 6.7 倍。此抽樣偏差已於儀表板註記揭露，並成為評估方法的一部分。

#2 2.3 文本特徵提取、主題分群與 CVE 抽取
對 788 篇非結構化文本，系統以 TF-IDF 特徵向量化捕捉資安關鍵字詞分布，並以 K-Means 演算法進行無監督主題分群，歸納威脅趨勢與攻擊型態（群集編號留存於語料之 cluster 欄位，供標註與抽樣使用）[1][2]。近重複事件以星狀分群去重：先挑出提到稀有 CVE 的「星」文章，其餘文章依共享 CVE、相同 URL 或標題重疊掛接，788 篇合併為 783 件事件。CVE 抽取以正規表示式比對並加入斷詞容錯——中文來源斷詞後常出現「CVE 2025 5777」的拆開形式，需正規化還原。全部語料共抽出 288 個不重複 CVE，再對照四份外部快照：EPSS（911 筆）、KEV（1,779 筆）[6]、CVSS（704 筆）[7] 與 CWE（287 筆，275 筆有值）[8]。快照遵循「資料時效即時效」原則：API 回傳之 data_as_of 取最舊快照日期。CVSS 取值順序為文章優先、CVE.org 補齊（154 筆），無法取得者僅 2 筆，覆蓋率 99.3%。

#2 2.4 可解釋加權風險評分
風險評分採雙軌設計。文章層以四因子固定權重計算 0–100 分：

@EQ 分數 = 100 × ( 0.50 × 嚴重度 + 0.30 × 利用機率 + 0.12 × 暴露程度 + 0.08 × CVE 具名 )　　(1)

其中利用機率在 CVE 已知時採用 EPSS 實測值[9]，已遭利用者直接計滿。即時評估層以五因子模型（資產關鍵度 0.30、威脅來源 0.26、漏洞嚴重度 0.20、利用成熟度 0.14、暴露程度 0.10）推導單一資產情境的分數，並接受在地情資關聯與資料敏感度調整項。兩條路徑皆拒絕黑盒：每一分都可逐項拆解，前端以決策路徑晶片呈現因子貢獻。取捨值得明說——若以邏輯回歸重新擬合權重，排序 AUC 可達 0.897，但產品採用固定權重，犧牲約 0.05 的 AUC 換取「每個分數都能說出構成」[3][4]。

#2 2.5 修補優先級與曝險推斷
修補清單以 CVE 為單位聚合：取該 CVE 所有報導中的最高 CVSS 與最高 EPSS，並標記是否落入 KEV。分級規則依 SSVC 之 Deployer 角色設計[10]：KEV 命中直接列 P1；EPSS 達 0.10 或 CVSS 達 9.0 列 P2；其餘為 P3。曝險偏移僅作用於 P2／P3：對外曝險升一級、內網降一級；KEV 永不降級。SLA 對應為 P1 24 小時、P2 7 天、P3 30 天，符合以風險為基礎的修補週期建議[12]。現行 288 個 CVE 之分級結果為 P1 131、P2 134、P3 23；曝險來源中資產清單比對 105 筆、情資描述 16 筆、產品名推斷 6 筆，其餘 161 筆維持未知並於介面明示。

#2 2.6 全球盲點補強
只呈現「看到的」會讓使用者誤以為清單即全部。系統以語料日期窗（2024-01-18 至 2026-11-13）為分母，取 KEV 加入日落於窗內之 711 筆，減去語料涵蓋的 80 筆，得 631 筆未收錄，覆蓋率僅 11%，其中 81 筆與勒索軟體活動相關。該 631 筆因缺乏曝險與文章可追溯，刻意不併入主清單，而以獨立頁面（/api/v1/kev-uncovered）呈現，把「系統邊界」變成可決策的資訊。

#2 2.7 評估方法與結果
評估分三層。分類品質：100 筆 held-out 語料由兩人獨立標註、第三人依判定表裁決，同意率 87%、κ=0.818，裁決後準確率 73%（多數類別基準 44%）；早期 in-sample 的 91% 屬調參資料，不對外引用[5]。排序有效性：以「是否落入 KEV」為黃金標準，交叉驗證 AUC——本系統 0.853、僅 EPSS 0.827、純 CVSS 0.561，precision@10 為 1.00。時間切分回測：以 2026-05-27 為切點，測試窗口 273 筆（169 筆已標註）分類準確率 0.88、排序 AUC 0.87。限制誠實揭露：EPSS／KEV 快照為 2026 年 11 月版本，無法還原「當時」的利用機率。結果彙整如表 3、排序比較如圖 2。

#1 3. 系統創新性與技術亮點（權重 15%）
#2 3.1 全球預警與在地落地雙軌融合
國際平台對台灣來源覆蓋不足。本專題納入 164 篇台灣情資，將 69 個具台灣通報紀錄的 CVE 標記為「本地通報」供一鍵篩選，即時評估亦加入在地情資關聯調整項，消弭單一來源偏誤。
#2 3.2 可解釋加權模型取代黑盒
傳統評分模型難以向主管解釋。本系統的四因子文章評分與五因子即時評估皆為固定公開權重，任一 CVE 的 P1 判定可回溯至規則與快照資料，決策路徑以晶片呈現，增強 CISO 決策信任度。
#2 3.3 自動化 Playbook 應變劇本
針對辨識出的威脅類別與優先級，系統自動對應可執行的處置步驟（如 P1 惡意威脅：阻斷連線、盤點帳號、留存日誌、通報 CERT），what-if 對照更直接回答「加裝哪一項控制可降級」。
#2 3.4 盲點補強與誠實邊界
多數工具只呈現「我看到的」。本系統以 KEV 為鏡量化覆蓋僅 11%，將 631 筆未收錄漏洞製成獨立清單，把「未知的未知」轉化為可管理的風險輪廓。

#1 4. 實用性與防禦落實（權重 15%）
#2 4.1 日常作業流程
平台面向三種流程：例行批次——每週進入修補清單，依 P1–P3 與 SLA 排定工單並匯出 CSV，無需手動輸入；事件觸發——收到新情資即用即時評估取得分數、等級與劇本；情境校正——清單上的 CVE 若與自身環境不同，可帶入評估覆寫等級。四個工作區（總覽／修補／評估／情資）對應四種流程。
#2 4.2 P1–P3 處置矩陣與 SLA 規範
P1 事件 24 小時內完成處置，P2 於 7 天內完成，P3 於 30 天內納入例行更新；KEV 命中者即使為內網資產亦須 24 小時內處理，不得降級。每一等級的觸發條件（KEV、EPSS 門檻、CVSS 門檻、曝險方向）皆為公開規則，可直接對照法遵查核。
#2 4.3 EPSS 與 CISA KEV 雙重評估
修補順序同時考慮「高利用機率（EPSS）」與「已知遭武器化利用（KEV）」：EPSS 達 0.10 進入 P2 門檻，KEV 命中直接 P1。回測證明此組合優於單一來源（AUC 0.853 對 0.827／0.561）。
#2 4.4 弱點類型篩選與工單分流
系統依 CWE 將 275 個漏洞歸入十二類弱點類型（遠端執行 32、認證繞過 52、記憶體安全 60 等），工程師可依類型篩選並分流工單；13 個尚無 CWE 紀錄者標示「未標示」，不冒充分類成功。

#1 5. 預期效益與結論（權重 25%）
#2 5.1 量化效益（預估值，待上線數據校正）
以一名資安工程師每週 15 小時人工瀏覽新聞估算，自動化分群與評分可將情資篩選時間降至 2 小時、縮短 80% 以上，處置回應速度提升約 3 倍；對比年費數百萬台幣的國際商業 CTI 平台，本方案可降低七成以上情資採購成本。上述為預估目標值，正式效益需以試用單位的工時紀錄校正。

#2 5.3 商業化可行性與產值預估
計算口徑：以台灣中大型企業（約 1,200 家）與中小型 MSSP（約 50 家）為目標客群，採 SaaS 年費訂閱制，企業基礎版年費新台幣 20 萬元、專業版（含 API 串接與客製語料）50 萬元；假設首年（2027 年）滲透率 2.5%（25 家企業與 5 家 MSSP）。據此 2027 年度營收預估落於新台幣 650 萬至 900 萬元（區間跨度約 38%，≤50%），第二年起邊際維護成本趨近於零，三年內可望達 2,000 萬元以上。須標注：滲透率為假設值，待初版釋出後以試用申請數校正。差異化可驗證者有三：其一，在地語料與全球情資雙軌加權——以 TWCERT/iThome 事件對照國外平台進行雙盲分類測試；其二，可解釋評分與自動化 Playbook——量測從接收情資到產出處置劇本的平均耗時；其三，EPSS＋KEV 盲點補強——以 /api/v1/kev-uncovered 驗證系統能否揪出「無新聞報導但已遭實際利用」的高風險漏洞。企業購買理由：成本面——相比年費動輒 300 萬台幣以上的國際平台，本方案降低七成以上採購成本；效益面——每週情資過濾自 15 小時降至 2 小時，P1 事件有 24 小時阻斷 SLA 指導；風險面——KEV 永不降級與覆蓋缺口揭露，降低「自以為都看到了」的誤判風險。可執行結論：以「降低資安人力過載＋確保 P1 阻斷 SLA」為核心訴求，提供 14 天免費 PoC 促成簽約。
#2 5.4 行銷與推廣策略
策略一，資安研討會與 CISO 交流會：受眾為高科技製造業與金融業資安長；渠道為臺灣資安大會（CYBERSEC）、iThome 專題講座與 LinkedIn 社群；動作文案「別讓情資成為噪音——788 篇情資如何 3 秒轉化為 P1 回應 SLA？預約 PoC 體驗」；預期（假設值）現場觸及 300 位決策者、15 份 PoC 申請。策略二，MSSP 與 SI 整合商技術合作：受眾為中小型 MSSP 與系統整合商技術長；渠道為 B2B 白皮書與 REST API 技術研討會；動作「無縫整合 FastAPI 微服務 API，為客戶提供全球預警與在地落地雙重防禦」；預期（假設值）觸及 20 家廠商、完成 3 家通路簽約。策略三，開源社群與 DevSecOps 內容行銷：受眾為 DevSecOps 工程師與大專資安社群；渠道為 GitHub、iThome 鐵人賽與 TechBlog；動作「完整 PoC 代碼與 788 篇語料分析範例大公開」；預期（假設值）GitHub 200 顆 Star、專欄累計 5,000 次瀏覽。
#2 5.5 結論與未來藍圖
本專題以 788 篇情資、288 個 CVE 與四份官方快照，建構從新聞到修補工單的完整決策鏈，並證明「可解釋」與「夠準確」可以同時交付——排序 AUC 0.853 勝過單一來源，分類 73%（κ 0.818）優於簡易基線，且每項限制皆已揭露。未來藍圖有四：快照自動化（排程器每日更新 EPSS／KEV）、資產串接（CMDB 匯出取代示範資產，曝險覆蓋自 44% 提升）、混合智能（以大型語言模型生成摘要與建議，保留規則層為可稽核底座）、流程整合（產出 Jira 與 ServiceNow 相容工單格式，直通既有維運流程）。
