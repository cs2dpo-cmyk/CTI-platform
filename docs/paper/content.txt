@ABSTRACT 資安長常面臨情資量遠大於處理量的困境：每天數百則新聞、持續新增的漏洞，卻缺乏可執行的排序依據。本研究開發「CTI 資安風險決策支援平台」，以 788 篇情資建構 35 個月語料，經 TF-IDF 與 K-Means 梳理主題，抽取 288 個 CVE 對照 KEV、EPSS、CVSS、CWE 四項官方資料。系統以可解釋加權模型評分——文章依四因子（50／30／12／8）、即時評估依五因子——輸出一份排序好的修補工單，並依 KEV、EPSS 與曝險規則決定優先級（P1 24 小時、P2 7 天、P3 30 天）。回測顯示，本系統排序已遭利用漏洞的能力（交叉驗證 AUC 0.853）優於單用 CVSS（0.561）；規則式分類之 held-out 準確率 73%（Cohen's κ=0.818）。平台以 FastAPI 與 SQLite 實作並部署於 Render 雲端，讓部署商由「讀新聞」轉為「看清單」。
@KEYWORDS 威脅情資 (CTI)；資安風險評估；EPSS / CISA KEV；TF-IDF 與 K-Means；CISO 決策支援儀表板

@TCAP 表1 專題核心價值（Core Value）
| 將分散的公開資料（KEV、EPSS、CVSS、CWE）組裝成一份可執行、可稽核的修補優先清單，讓資安決策者用最小時間完成「先修哪個」的判斷。

#1 1. 研究動機與背景（權重 15%）
企業資安的核心困境是「情資海量卻無法落地」：The Hacker News 每月約 250 篇，TWCERT/CC 與 iThome 持續產出在地公告[1][2]，中小企業資安編制通常僅一至三人。本專題語料為 2024-01 至 2026-11 的 788 篇、783 件事件，標題含 CVE 者僅約一成。
更根本的問題是「嚴重度與利用風險不對等」。以 CISA KEV 為「已遭實際利用」的依據回測：僅用 CVSS 排序的交叉驗證 AUC 只有 0.561（幾近隨機）、僅用 EPSS 0.827、本系統加權模型 0.853。只看 CVSS，有一半的修補順序是錯的。
本專題據此設定三項目標：把新聞轉成帶期限的工單、讓每一級都能說出理由、以固定權重取代黑箱。

#1 2. 系統方法與實作過程（權重 30%）
#2 2.1 系統架構與技術棧
系統採五層架構（圖 1）：資料來源層整合三家新聞源；語料層以 SQLite 儲存並去重；對照層將 CVE 與四份官方快照及資產清單比對；決策層執行分群、分類、評分與優先級推算；介面層以 FastAPI 提供八個端點，前端為原生 JavaScript 與 Chart.js。分層使錯誤可定位到層級，後端部署於 Render。

#2 2.2 語料建置與分層取樣
依抓取順序取樣會集中於最近兩月（原始版本 77%），且 iThome 深層頁面受限（403 與 robots）僅留近期 50 篇；故採分層取樣：每月 15 篇國際＋5 篇台灣，鋪平 35 個月。語料分兩層：平衡對照 200 篇（台 100：國 100）供跨區比較，自然語料 588 篇依真實比例。並存之因：自然語料台灣僅占 21%，只用平衡樣本則放大急迫性（P1 20% 對 3%）。

#2 2.3 主題分群與 CVE 抽取
788 篇文本先以 TF-IDF 向量化、再以 K-Means 分群歸納主題（群集存於 cluster 欄位），實作採 scikit-learn[3][4][5]。近重複事件以星狀分群去重（稀有 CVE 文章為「星」，其餘依共享 CVE、同 URL 或標題掛接），788 篇合併為 783 件。CVE 以正規表示式抽取並容忍斷詞拆解（「CVE 2025 5777」還原為 CVE-2025-5777），共得 288 個。對照四份快照：EPSS 911、KEV 1,779[6]、CVSS 704[7]、CWE 287（275 有值）[8]；CVSS 以文章優先、CVE.org 補齊 154 筆，僅 2 筆無法取得。

#2 2.4 可解釋加權風險評分
文章層以四因子固定權重計算 0–100 分：

@EQ 分數 = 100 × ( 0.50 × 嚴重度 + 0.30 × 利用機率 + 0.12 × 暴露程度 + 0.08 × CVE 具名 )　　(1)

利用機率在 CVE 已知時採 EPSS 實測值[9]，已遭利用者直接計滿。即時評估層改用五因子（資產關鍵度 0.30、威脅來源 0.26、漏洞嚴重度 0.20、利用成熟度 0.14、暴露程度 0.10），並接受在地情資與資料敏感度調整。兩條路徑皆拒絕黑盒：每一分都能逐項拆解。若以邏輯回歸重新擬合權重，AUC 可達 0.897；產品仍採固定權重，以約 0.05 的 AUC 換取可解釋性。

#2 2.5 修補優先級與曝險推斷
清單以 CVE 為單位聚合：取該 CVE 的最高 CVSS 與最高 EPSS，並標記是否落入 KEV。分級依 SSVC 之 Deployer 角色設計[10]：KEV 命中列 P1；EPSS 達 0.10 或 CVSS 達 9.0 列 P2；其餘 P3。曝險偏移僅作用於 P2／P3：對外升一級、內網降一級，KEV 永不降級。SLA 為 P1 24 小時、P2 7 天、P3 30 天，對應以風險為基礎的修補週期建議[11]。現行 288 個 CVE 為 P1 131、P2 134、P3 23；曝險來源中資產清單 105 筆、情資描述 16 筆、產品名推斷 6 筆，其餘 161 筆維持未知並於介面明示。

#2 2.6 評估方法與結果
評估分三層。分類品質：100 筆 held-out 語料由兩人獨立標註、第三人依判定表裁決，同意率 87%、κ=0.818，裁決後準確率 73%（多數類別基準 44%）；早期 in-sample 的 91% 屬調參資料，不對外引用[12]。排序有效性：以「是否落入 KEV」為黃金標準，交叉驗證 AUC 為本系統 0.853、僅 EPSS 0.827、純 CVSS 0.561，precision@10 為 1.00。時間切分回測：以 2026-05-27 為切點，測試窗口 273 筆（169 筆已標註）分類準確率 0.88、排序 AUC 0.87。限制誠實揭露：EPSS／KEV 快照為 2026 年 11 月版本，無法還原當時的利用機率。結果彙整如表 2，排序比較如圖 2。

#1 3. 系統創新性與技術亮點（權重 15%）
#2 3.1 可解釋加權模型取代黑盒
固定公開權重使任一 P1 判定可回溯至規則與快照；決策路徑以晶片呈現，主管問「為何是 P1」可答「KEV 命中＋對外曝險」。
#2 3.2 自動化 Playbook 應變劇本
依類別與優先級自動對應處置步驟（如 P1：阻斷連線、盤點帳號、留存日誌、通報 CERT）；what-if 回答「加裝哪項控制可降級」。

#1 4. 實用性與防禦落實（權重 15%）
#2 4.1 日常作業流程
三種流程：例行批次（每週依 P1–P3 與 SLA 排工單並匯出 CSV）、事件觸發（新情資即評估取得分數與劇本）、情境校正（清單 CVE 若環境不同可覆寫等級）。
#2 4.2 P1–P3 處置矩陣與 SLA
P1 須 24 小時內處置、P2 7 天、P3 30 天；KEV 命中者即使內網亦須 24 小時內處理。各級觸發條件（KEV、EPSS、CVSS、曝險方向）皆為公開規則，可直接對照法遵查核。
#2 4.3 EPSS 與 KEV 雙重評估、弱點類型分流
修補順序同時考慮 EPSS 與 KEV：EPSS 達 0.10 進入 P2、KEV 命中直接 P1，回測顯示優於單一來源。系統另依 CWE 將 275 個漏洞歸入十二類（遠端執行 32、認證繞過 52、記憶體安全 60 等），供工程師篩選分流。

#1 5. 預期效益與結論（權重 25%）
#2 5.1 量化效益（預估值，待上線數據校正）
以每週 15 小時人工瀏覽新聞估算，自動化分群可將篩選降至 2 小時（縮短 80% 以上）、回應速度提升約 3 倍；相較年費數百萬台幣的國際 CTI 平台可降低七成成本（預估，待工時校正）。

#2 5.3 商業化可行性
計算口徑：目標客群為台灣中大型企業（約 1,200 家）與中小型 MSSP（約 50 家），SaaS 年費制基礎版 20 萬元、專業版 50 萬元；假設 2027 年滲透率 2.5%（25 家企業＋5 家 MSSP），營收預估新台幣 650–900 萬元（跨度約 38%），三年內可望達 2,000 萬元（滲透率為假設值）。差異化有三：在地與全球情資雙軌加權、可解釋評分與自動化 Playbook、EPSS 與 KEV 雙重排序，皆可以雙盲測試與耗時量測驗證。
#2 5.4 行銷與推廣策略
策略一，研討會與 CISO 交流會：受眾為製造與金融業資安長，渠道為臺灣資安大會與 iThome 講座；文案「別讓情資成為噪音——788 篇情資如何 3 秒轉化為 P1 回應 SLA」；預期（假設）觸及 300 位決策者、15 份 PoC。策略二，MSSP／SI 合作：受眾為 MSSP 技術長，渠道為白皮書與 API 研討會；文案「無縫整合 FastAPI 微服務，全球預警與在地落地雙重防禦」；預期（假設）20 家廠商、3 家簽約。策略三，開源社群：渠道為 GitHub 與 iThome 鐵人賽；文案「PoC 與語料分析大公開」；預期（假設）200 顆 Star、5,000 次瀏覽。
#2 5.5 結論與未來藍圖
本專題建構了從新聞到修補工單的決策鏈，證明可解釋與夠準確能同時交付：AUC 0.853 勝過單一來源，分類 73%（κ 0.818）優於基線。未來藍圖：快照自動化、CMDB 串接、LLM 摘要（規則層為稽核底座）、輸出 Jira／ServiceNow 工單。
