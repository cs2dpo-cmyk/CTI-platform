## 1. 一頁看懂

**一句話**：把每天幾百則資安新聞，轉成「**今天該先修哪幾個漏洞**」的有序清單。

**它解決的落差**：

```
新聞：今天有 80 則新情資           決策：我今天只有 2 小時，先修哪 3 個？
（數量太多、沒有優先級）    →      （需要排序、期限、理由）
```

**三個核心動作**：

1. **讀**：抓新聞 → 抽出漏洞編號（CVE）→ 對照官方資料（EPSS 利用機率、KEV 已利用清單、CVSS 嚴重度、CWE 弱點類型）
2. **排**：套用可解釋的規則 → 每個 CVE 得到 P1／P2／P3 與 SLA（24 小時／7 天／30 天）
3. **說**：每個結果都附「為什麼」——哪個訊號觸發了這個等級，可稽核、可爭論

**目前規模**：788 篇情資、741 件事件、288 個 CVE、35 個月（2024-01～2026-11）。

## 3. 市場需求與企業痛點

### 3.1 大企業（與中型企業）真正的痛點

| # | 痛點 | 具體表現 | 本專題怎麼回應 |
|---|---|---|---|
| 1 | **情資量遠大於處理量** | 團隊 1～3 人，每天數百則新聞與告警，只能憑印象挑 | 自動抽出 CVE 並排序，把「讀」壓成「看清單」 |
| 2 | **不知道哪個先修** | CVSS 分數高的不一定被利用（本專題實測：只用 CVSS 排序的 AUC 僅 0.47～0.56） | 引入 EPSS（利用機率）與 KEV（已遭利用事實） |
| 3 | **修補期限沒有依據** | 合規要求 24 小時／7 天／30 天，但沒人說得出「為什麼這個是 24 小時」 | 每個等級都有可稽核的觸發路徑（KEV＋曝險 → P1） |
| 4 | **在地情資被忽略** | 國際工具不讀 TWCERT／台灣新聞，台灣的公告與事件被漏掉 | 語料含 164 篇台灣來源，並標記「本地通報」CVE |
| 5 | **工具之間斷裂** | SIEM 告警、弱點掃描、新聞情資三套系統各說各話 | 以 CVE 為共同鍵，把三者串成一份清單 |
| 6 | **決策無法解釋** | 主管問「為什麼先修這個」，答不出來 | 決策路徑晶片＋因子貢獻＋what-if 對照 |
| 7 | **不知道漏了什麼** | 只看到有報導的漏洞，沒報導的就消失 | 「已知被利用但未收錄」頁面，量化覆蓋缺口 |

### 3.2 現有工具與缺口

| 工具類型 | 代表 | 強項 | 缺口（本專題切入點） |
|---|---|---|---|
| 弱點管理（VM） | Tenable、Qualys | 掃描準確、資產完整 | 只知道「你有什麼漏洞」，不知道「哪個正在被利用」 |
| SIEM／SOAR | Splunk、Sentinel | 日誌關聯、自動化 | 需要大量工程與授權成本；不擅长跨來源排序 |
| 情資平台（TIP） | MISP、Anomali | 情資彙整、IOC 分享 | 產出的是情資，不是「排好的修補工單」 |
| 官方標準 | EPSS、KEV、CWE、SSVC | 客觀、公開 | **是零件不是產品**：需要有人把它們組起來、在地化、給出期限 |

**本專題的定位**：不是取代上面任何一個，而是把它們的**公開資料組裝成一個可執行的決策層**，並針對「部署商（Deployer）」——負責自家內部資產與修補分流的人——設計。

### 3.3 為什麼是「部署商（Deployer）」

SSVC（CISA 的漏洞處置決策框架）把利害關係人分成四類：**Patch Supplier、Deployer、Coordinator、Author**。
本系統假設使用者是 **Deployer**：他不負責寫補丁、也不負責協調，他的問題只有一個——

> 「我手上這些系統，哪一個現在最該修？」

所有設計（以 CVE 為單位、曝險權重、SLA 期限、匯出 CSV）都由此推導。

## 4. 名詞表（0 基礎先看這裡）

| 名詞 | 白話解釋 |
|---|---|
| **CTI** | 網路威脅情資：關於「誰在攻擊、用什麼手法、攻擊哪裡」的資訊 |
| **CVE** | 漏洞的身分證號，例如 `CVE-2024-3400`。全球唯一，一個漏洞一個號 |
| **CVSS** | 漏洞的「嚴重度分數」0～10，由漏洞本身推得，**不代表現在有人利用** |
| **EPSS** | 漏洞「未來 30 天被利用的機率」0～1，由 FIRST 每天用機器學習算出 |
| **KEV** | CISA 的「已知被利用漏洞」清單，**代表已經有實際攻擊**，共 1,779 筆 |
| **CWE** | 弱點的「種類」，例如 CWE-78 指令注入、CWE-79 XSS |
| **SSVC** | 一套決策框架：依「利用狀態 × 曝險 × 影響」決定處置動作 |
| **SLA** | 服務水準協議，在這裡指「多久內要修好」 |
| **P1／P2／P3** | 本系統的優先級：P1 24 小時、P2 7 天、P3 30 天 |
| **快照（snapshot）** | 外部資料在某一天的副本，附上擷取日期，避免「數字從哪來」說不清 |
| **曝險（exposure）** | 這台機器是否可從外網碰到。對外＝風險高，內網＝風險低 |
| **CTI 語料** | 本系統收集的新聞文章集合（788 篇） |

## 5. 系統架構（五層）

```
① 資料來源層   The Hacker News（國際）｜TWCERT（台灣政府）｜iThome（台灣媒體）
        ↓ 抓取＋分層取樣
② 語料層       788 篇 → 741 件事件（去重）→ 抽出 288 個 CVE
        ↓ 對照官方資料
③ 情資對照層   EPSS（機率）｜KEV（已利用）｜CVSS（嚴重度）｜CWE（類型）｜資產清單
        ↓ 規則推論
④ 決策層       規則分類（4 類）→ 可解釋評分（5 因子）→ 修補優先級（P1–P3＋SLA）
        ↓ HTTP API
⑤ 介面層       FastAPI（/api/v1）→ 儀表板 4 分頁（總覽／修補／評估／情資）
```

**為什麼要分層**：每一層都可以單獨驗證。語料錯了只影響語料層的測試；排序錯了不會動到分類器。這讓「出問題時知道去哪一層找」變成可能。

## 6. 資料層：語料與快照

### 6.1 三個來源，各自的限制

| 來源 | 性質 | 產能 | 我們取用 | 限制 |
|---|---|---|---|---|
| The Hacker News | 國際媒體 | 每月約 250 篇 | 每月 15 篇 | 英文、偏國際視角 |
| TWCERT/CC | 台灣政府 CERT | 每月約 5 篇 | 幾乎全收 | 量少、偏公告格式 |
| iThome | 台灣科技媒體 | 每日數十篇 | 僅近期 50 篇 | 深頁 403、robots 禁止系統性抓取 |

**為什麼要分層取樣**：如果照抓取順序取，語料會被「最近兩個月」塞滿（原始版本 77% 集中在 2 個月）。
因此改成「**每月固定抽 15 篇國際＋5 篇台灣**」，把 35 個月鋪平，每月 17～20 篇。

### 6.2 語料的兩層設計（重要）

| 層 | 篇數 | 抽樣方式 | 用途 |
|---|---|---|---|
| **平衡對照** | 200 | 台灣 100：國際 100（刻意 50:50） | 台／國**結構比較**（類別佔比） |
| **自然語料** | 588 | 依真實發布比例 | 反映**真實分布**（風險占比） |

**為什麼不能只用一種**：

- 只用自然語料 → 台灣只佔 21%，任何「台灣 vs 國際」的比較都會被國際量體淹沒
- 只用平衡樣本 → 會**放大急迫性**：實測 P1 佔比在平衡樣本是 20%，自然語料只有 3%

所以兩者並存，並在儀表板明講「本頁含 200 筆平衡對照樣本」。

### 6.3 外部快照（每個數字都有來源）

| 快照 | 檔案 | 內容 | 更新方式 |
|---|---|---|---|
| EPSS | data/epss.json | 911 個 CVE 的利用機率 | tools/refresh_snapshots.mjs |
| KEV | data/kev_ids.json、kev_full.json | 1,779 筆已利用漏洞 | 同上 |
| CVSS | data/cvss.json | 704 個 CVE 的嚴重度 | tools/refresh_cvss.py |
| CWE | data/cwe.json | 287 個 CVE 的弱點類型（275 有值） | tools/refresh_cwe.py |
| 資產 | data/assets.csv | 14 台示範資產 | tools/asset_import.py |

**data_as_of**：API 會回傳「最舊的那個快照日期」。為什麼取最舊？因為一份上週的 KEV 會讓整份回應的可信度不超過上週——不能只用最新的日期假裝新鮮。

## 7. 核心技術逐項解析

每一項都依「**做什麼 → 怎麼運作 → 為什麼用它 → 替代方案與取捨 → 限制**」說明。

### 7.1 規則式文章分類（4 類）

**做什麼**：把每篇文章分成 VULN（系統漏洞與修補）、MALWARE（惡意威脅與主動攻擊）、RESEARCH（前瞻研究與治理）、OTHER（產業動態）。

**怎麼運作**：`services/classify.py` 是一組**有順序的規則**，每條規則是一個關鍵詞／句型正則。判斷時從第一條往下比對，第一個命中就回傳該類別與「命中的規則」。

```
標題：「CISA 警告 Ivanti 漏洞已遭利用」
  → 規則 1（CVE + 已遭利用）命中 → VULN，理由：規則 1
```

**為什麼不用機器學習**：

| 考量 | 規則式（採用） | 機器學習 |
|---|---|---|
| 可解釋 | 每篇都能說「因為命中規則 3」 | 需要 SHAP 等額外工具才能解釋 |
| 資料量 | 788 篇也堪用 | 深度學習通常需要上萬筆 |
| 維護 | 改一條規則立即生效 | 要重新訓練、重新驗證 |
| 稽核 | 規則可被逐條審查 | 權重是黑箱 |

**替代方案與取捨**：TF-IDF＋SVM 或 BERT 微調在樣本足夠時準確率更高，但會犧牲「每個判斷都能指回一行規則」這件事。本專題選擇可稽核性。

**限制（實測）**：held-out 準確率 **73%**（雙人標註、κ=0.818）。最大誤差來源是「週報／彙整型文章」——它們同時提到多個事件，分類慣例本身有爭議（語料中僅 2.5%，已寫進限制）。

### 7.2 CVE 抽取

**做什麼**：從標題與內文找出漏洞編號，格式化成 `CVE-YYYY-NNNN`。

**怎麼運作**：正則比對＋**斷詞容錯**。中文來源（TWCERT）在斷詞後常把編號拆開，例如「CVE 2025 5777」，所以除了標準格式，還要處理「CVE + 空白 + 年份 + 空白 + 序號」的變體，再正規化成 `CVE-2025-5777`。

**為什麼需要**：CVE 是**唯一能把三個世界串起來的鍵**——新聞（文章）、官方資料（EPSS/KEV/CVSS/CWE）、企業資產（我有哪些系統）。沒有 CVE，就只能做文本分析，做不了決策。

**限制**：只有 12% 的情資（92/741）標題中含 CVE，所以能進入修補清單的只有一部分；其餘留在「情資流」供人閱讀。

### 7.3 近重複事件偵測（去重）

**做什麼**：同一件事常被多家媒體報導（例如 CVE-2024-3400 被 7 家寫），若不處理，統計會重複計算、清單會膨脹。

**怎麼運作**：**星狀分群（star clustering）**：
1. 先挑「星」——提到稀有 CVE 的文章（資訊量最高）
2. 其餘文章若與某顆星共享 CVE、或 URL 相同、或標題高度重疊，就掛到該星底下
3. 每群只留一篇代表，其餘標記 `duplicate_of`

**為什麼用它**：不需要指定群數（K-Means 要），也不需要兩兩比對全部（O(n²)）。對「同一事件被重複報導」這種資料形狀，星狀分群的假設最貼近現實。

**結果**：788 篇 → **741 件事件**（5 篇重複被合併，另有 URL 重複在建置時已剔除）。

### 7.4 可解釋風險評分（文章層）

**做什麼**：把一篇文章轉成 0～100 的風險分數，並拆解成 5 個因子的貢獻。

**怎麼運作**：

```
分數 = 100 × ( 0.50 × 嚴重度
             + 0.30 × 利用機率（有 CVE 時用 EPSS 實測值）
             + 0.12 × 暴露程度
             + 0.08 × CVE 具名 )
```

**為什麼是這組權重**：嚴重度是文獻與實務最常用的維度，但單看它會失準，所以把「有沒有被利用」（EPSS/KEV）拉到 30%；暴露與具名是輔助訊號，權重壓低避免噪音放大。權重是**固定且公開**的，任何人都能重算。

**替代方案與取捨**：邏輯回歸／重新擬合權重可把交叉驗證 AUC 從 0.85 拉到 0.89，但係數會隨資料漂移且難以向主管解釋；本專題選擇固定權重，把差距寫進文件。

### 7.5 修補優先級（CVE 層級）— 系統的核心

**做什麼**：把 288 個 CVE 排成 P1／P2／P3，各附 SLA 與理由。

**怎麼運作**（`services/patch_priority.py`）：

```
基礎等級：
  P1  ← 在 CISA KEV（已遭實際利用）
  P2  ← EPSS ≥ 0.10 或 CVSS ≥ 9.0
  P3  ← 其餘

曝險偏移（只影響 P2／P3，KEV 永不降級）：
  對外曝險 → 升一級（P3→P2、P2→P1）
  內網     → 降一級（P2→P3）
  未知     → 不動

SLA：P1 24 小時｜P2 7 天｜P3 30 天
```

**為什麼這樣設計**：這是 **SSVC 概念 + 公開資料**的落地。SSVC 說「已遭利用」應該最優先，KEV 提供了這個事實；「利用可能性」用 EPSS 補；「曝險」用企業自己的資產清單補。三者疊起來就是可執行的順序。

**結果（現況）**：P1 131、P2 134、P3 23。其中 **0 個 KEV 被降到 P1 以下**（可驗證的不變式）；只有 2 個 CVSS ≥ 9 的 CVE 因為被標記為內網而落在 P3（刻意設計）。

**限制**：只有「新聞提到的 CVE」會進清單，覆蓋率見 7.11。

### 7.6 EPSS（利用機率）

**是什麼**：FIRST 每天發布的分數，預測「某 CVE 在未來 30 天內被利用的機率」（0～1）。

**原理**：用機器學習（梯度提升樹）以「漏洞特徵、威脅情報、時間」等特徵預測是否會被利用，並以歷史資料校準。

**我們怎麼用**：有 CVE 就查實際分數（不是文字推測）；分數 ≥ 0.10 進入 P2 門檻；UI 以進度條呈現。

**限制**：EPSS 是**機率**，不是「已經被利用」的證據；也不能回答「這台機器會不會被打」。

### 7.7 KEV（已知被利用漏洞）

**是什麼**：CISA 維護的清單，只收「已觀察到實際利用」的漏洞（目前 1,779 筆）。

**我們怎麼用**：命中即 **P1（24 小時）**，且**永不因曝險而降級**——已遭利用的漏洞，就算在內網也要現在處理。

**限制**：CISA 視角以美國政府與產業為主；部分區域性漏洞不會進榜。

### 7.8 CVSS（嚴重度）

**是什麼**：0～10 的漏洞嚴重度，來自漏洞本身的技術特徵。

**我們怎麼用**：**文章優先、CVE.org 補齊**。文章若寫了分數（例如「CVSS 9.8」）就用文章的（可追溯回那則報導）；沒寫才查 CVE.org 快照，並在 UI 標「官」字區分來源。

**為什麼要補**：原本只有 48% 的 CVE 有分數（新聞常不寫），補齊後 **286/288**，剩下 2 個真的查不到（顯示「—」）。

**限制**：CVSS 衡量「有多嚴重」，不衡量「會不會被利用」——這也是為什麼只用 CVSS 排序的 AUC 只有 0.47～0.56。

### 7.9 CWE（弱點類型）

**是什麼**：缺陷分類法（CWE-78 指令注入、CWE-79 XSS、CWE-287 認證問題…）。

**我們怎麼用**：
1. 提供**弱點類型篩選**：遠端執行 32、認證繞過 52、記憶體安全 60…
2. 在即時評估中作為「這是哪種漏洞」的證據
3. **不用它決定 VULN／MALWARE**——它是缺陷分類，不是新聞分類

**限制**：13 個 CVE 尚無 CWE 紀錄（顯示「未標示」）。

### 7.10 曝險推斷（Exposure Resolution）

**做什麼**：判斷某個 CVE 影響的系統「是否可從外網碰到」。

**怎麼運作**（優先序，前者勝後者）：

```
人工指定 → 資產清單比對 → 情資描述（"internet-facing"） → 產品名推斷 → 未知
```

**為什麼需要**：同一個漏洞，對外網站與內網資料庫的處理順序完全不同。沒有曝險，優先級只能靠嚴重度，會把內網的低風險項目排在外網高風險之前。

**限制**：目前資產清單是 14 台示範資料，覆蓋率約 44%；其餘靠推斷或維持未知。

### 7.11 覆蓋缺口（KEV 未收錄）

**做什麼**：回答「我的語料漏掉了哪些已知被利用的漏洞」。

**怎麼運作**：以語料日期窗（2024-01-18～2026-11-13）為分母，取「KEV 加入日落在窗內」的 711 筆，減去語料涵蓋的 80 筆 → **631 筆未收錄**。

**為什麼要做**：只呈現「我看到的」會讓人誤以為那就是全部。把缺口攤開，才知道系統的邊界在哪。

**限制**：這 631 筆沒有曝險、沒有文章可追溯，因此**刻意不併入主清單**，只作為「你沒看到什麼」的補充檢視。

### 7.12 即時評估（單一情境）

**做什麼**：使用者輸入一台系統與一個情境，得到分數、等級、處置劇本。

**怎麼運作**：
1. 六個輸入（資產類型、威脅來源、類別、曝險、利用成熟度、控制項）
2. 五個因子加權 → 分數
3. 調整項（在地情資 +3、區域差異）
4. 得分級（P1 ≥ 80、P2 ≥ 66、P3 < 66）與劇本
5. **what-if**：用同一組條件再跑兩次（加一項控制項／改內網），回答「要怎麼降級」

**為什麼需要**：清單是**批次**（288 個一起看），評估是**單件**（我這一台）。兩者解決的問題相反：清單回答「先修哪個」，評估回答「我這台有多危險、怎麼降」。

### 7.13 分類建議（CVE Context）

**做什麼**：輸入 CVE，系統自動判斷它是「漏洞」還是「攻擊事件」，並說明依據。

**怎麼運作**：語料中所有提到該 CVE 的文章 → 統計類別 → 多數決（平手時選 VULN）；同時附上 KEV／EPSS／CVSS／CWE 作為證據。

**為什麼**：使用者不該需要記得「VULN 和 MALWARE 怎麼分」。系統給建議，人保留覆寫權。

### 7.14 後端框架（FastAPI + Pydantic + SQLAlchemy）

| 技術 | 做什麼 | 為什麼選它 |
|---|---|---|
| **FastAPI** | 提供 REST API、自動產生 OpenAPI 文件 | 型別驅動、開發快、自帶 /docs，適合展示與驗證 |
| **Pydantic v2** | 驗證請求與回應格式 | 契約明確；前端與文件都由型別推導 |
| **SQLAlchemy 2** | ORM 與查詢 | 可從 SQLite 換 PostgreSQL，不必改商業邏輯 |
| **SQLite** | 資料庫 | 單檔、零維運、部署簡單；本專題資料量（788 列）遠低於上限 |

### 7.15 前端（原生 JavaScript + Chart.js）

## 8. 原理：從資料到決策的公式

### 8.1 一條資料的旅程

```
新聞標題
  →（7.2）抽出 CVE
  →（7.3）判斷是否重複
  →（7.1）分類 4 類
  →（7.4）文章風險分數
  →（7.5）聚合到 CVE：取最高 CVSS、最大 EPSS、是否 KEV
  →（7.10）查曝險
  →（7.5）決定 P1/P2/P3 與 SLA
  → API → 儀表板
```

### 8.2 三個門檻的意義

| 門檻 | 值 | 意義 |
|---|---|---|
| EPSS 排程線 | 0.10 | 「10% 以上的機率被利用」→ 值得排入本週 |
| CVSS 嚴重線 | 9.0 | 「嚴重度極高」→ 即使利用機率未知也要排 |
| 評估分級 | 80／66 | 即時評估的分數換算成 P1／P2／P3 |

**為什麼是這些數字**：它們不是拍腦袋——EPSS 0.10 是實務常用的處置線（約對應「前 5% 高風險」），CVSS 9.0 是 CVSS 定義的 Critical 下限，80/66 則對應「P1 需要接近滿分風險」。所有數字都寫在程式常數裡，可被審查與調整。

### 8.3 為什麼「已遭利用」優先於「很嚴重」

```
嚴重度（CVSS）回答：這個漏洞如果被利用，後果多大？
利用事實（KEV）回答：它現在是不是已經被利用了？
機率（EPSS）回答：它接下來 30 天被利用的可能性多高？
```

一個 CVSS 10 但沒人利用的漏洞，與一個 CVSS 7 但正在被勒索集團利用的漏洞，**後者必須先修**。這是整個系統最核心的價值判斷，也是 SSVC 與 CISA KEV 的立場。

## 9. 評估方法：為什麼這些數字可信

### 9.1 分類器怎麼驗

| 步驟 | 做法 | 結果 |
|---|---|---|
| 標註 | 100 筆 held-out，**兩人獨立標**，第三人依指南裁決 | κ = 0.818（高度一致） |
| 規則化重標 | 把爭議類型寫成判定表後重標 54 列 | κ 從 0.679 升到 0.818 |
| 準確率 | 與裁決後的標籤比對 | **73%**（多數類 baseline 44%） |
| 誠實揭露 | 也公布兩位標註者原始分數 | 51% / 52%（差異來自類別慣例） |

**為什麼要雙人＋裁決**：單人標註會把「一個人的直覺」當成真理。兩個人的不一致率（κ）本身就是重要資訊——它告訴你「這個任務有多主觀」。

**重要警告**：91% 是 in-sample（規則調參用的那 100 筆），**不能對外引用**。對外一律 73%。

### 9.2 排序怎麼驗（KEV 當 ground truth）

把「是否有進 KEV」當作「是否真的被利用」的標準答案，比較不同排序法的 AUC：

| 排序方法 | 交叉驗證 AUC |
|---|---|
| 本系統（50/30/12/8） | **0.853** |
| 僅 EPSS | 0.827 |
| 僅 CVSS | 0.561 |
| 邏輯回歸（重新擬合） | 0.878 |
| 重新擬合權重 | 0.897 |
| **precision@10** | **1.00**（前 10 名全部命中） |

**怎麼看**：本系統勝過單用 EPSS（0.853 vs 0.827）與單用 CVSS（0.561）。差距不大，所以文件裡明講「AUC 的功勞主要屬於 EPSS，本系統的價值在於把機率轉成可執行的順序（SLA、曝險、資產）」。

### 9.3 時間怎麼驗

把語料按時間切兩段（切點 2026-05-27）：

| 窗口 | 筆數 | AUC | 備註 |
|---|---|---|---|
| 發展（之前） | 515 | 0.55 | 只有 24 筆有 CVE，樣本太小 |
| 測試（之後） | 273 | **0.87** | 169 筆已標註 |

**為什麼要做**：如果只用同一段時間的資料驗證，等於「考題就是練習題」。時間切分模擬「用過去預測未來」。

### 9.4 覆蓋率怎麼量

| 指標 | 值 |
|---|---|
| 語料 CVE 數 | 288 |
| KEV 全量 | 1,779 |
| 語料涵蓋的 KEV（全期） | 94（5.3%） |
| 語料涵蓋的 KEV（窗內） | 80 / 711（**11%**） |

**為什麼要公布**：不公布，讀者會以為清單就是全部。公布後，「補漏頁」才有意義，也知道系統的邊界。
